# R7 – Identity, reputation and the ledger question

The one-paragraph answer. "Unhackable reputation" splits into three claims of very different strength. **Identity integrity** (this message was signed by the controller of this identifier, and a stolen key cannot steal the identifier) is cryptographically achievable; KERI's pre-rotation is the mechanism. **Record integrity** (the history of what the agent did cannot be rewritten or shown differently to different readers) is achievable with append-only hash-chained logs plus witnesses; git plus countersigned receipts gets most of the way without any consensus. **Reputation meaning** (this agent is good) is a judgment computed by a reader, and it is always gameable: Douceur shows Sybil attacks cannot be ruled out without a trusted issuer or costly identity, Cheng and Friedman show no symmetric (global) reputation function is Sybil-proof, and Jøsang states flatly that no objective reputation exists, only X's view of T. So the design makes the first two unhackable, makes the third local, asymmetric and recoverable, and uses the house demotion rule as the recovery clock. Blockchain: **out of the core, optional as an anchor**, flipping to core only when the protocol carries rivalrous state (stake, payment, globally unique names among unknown writers).

## 1. Findings

**F1. Pre-rotation makes an identifier survive theft of its signing key.** A KERI inception event carries the current public key(s) and only a *digest* of the next key set; each rotation reveals the committed next keys and commits to a new digest. A thief holding the current private key cannot forge a rotation, because rotation must be signed by keys that were never exposed. The identifier (prefix) is derived from the inception event, so it is self-certifying and needs no registry. Failure prevented: key compromise equals identity loss (the Nostr failure, F9). Cost: the controller must keep a second key set offline; if both current and next keys are compromised, cryptographic recovery is gone and only a delegator or out-of-band process can help. Source: Smith, KERI, https://arxiv.org/abs/1907.02143 (2019, rev. 2025) · opened; KERI spec v1.1, https://trustoverip.github.io/kswg-keri-specification/ (2025–26) · opened.

**F2. Duplicity, not double-signing prevention, is KERI's security model.** Witnesses (chosen by the controller) sign receipts of key events; watchers (chosen by validators) keep the first version of each event they see, and any second, differently-signed version of the same event is *evidence* of compromise or malice. The spec's rule is roughly "first seen, always seen, never unseen". Failure prevented: an attacker quietly forking an identity's history. Cost: early, wide distribution of each event matters; a rotation after compromise races the attacker's first-seen copies. This is detection-plus-accountability rather than global agreement. Source: KERI spec v1.1 · opened.

**F3. Delegated identifiers give the operator a recovery lever over the agent.** A KERI delegate's inception and rotations must be anchored by a seal in the delegator's key event log; the delegator can approve, rotate or abandon the delegate. Failure prevented: an agent whose keys are wholly compromised is unrecoverable. Cost: the delegator becomes a dependency (and a target). Source: KERI spec v1.1 · opened.

**F4. did:plc shows a pragmatic priority-ordered recovery window.** Rotation keys are listed in descending authority; for 72 hours after an operation, a higher-ranked key can sign an operation pointing back to the last valid one, nullifying what a lower key did. The operation log is self-certifying, but a single directory server collects and orders it; the spec limits that server's possible attacks to denial and fork misordering. AT Protocol adds "adversarial migration": a user holding their own rotation key can leave a hostile host without its cooperation. Failure prevented: a stolen hot key or a hostile host capturing the account. Cost: a central directory; recovery bounded by a clock. Source: did:plc spec, https://web.plc.directory/spec/v0.1/did-plc (2023–) · opened; AT Protocol account migration, https://atproto.com/guides/account-migration · opened.

**F5. W3C DID Core and VC 2.0 are envelopes, not recovery mechanisms.** DID Core 1.0 (Recommendation, July 2022) defines syntax, documents, verification methods and controllers, and delegates key recovery to each DID method. VC Data Model 2.0 (Recommendation, 15 May 2025) defines issuer, holder, verifier and registry roles and securing by Data Integrity proofs or JOSE/COSE; it notes that a verifiable credential proves who signed a claim, not that the claim is true. Failure prevented: format fragmentation. Cost: JSON-LD weight; recovery and Sybil questions untouched. Source: https://www.w3.org/TR/did-1.0/ (2022) · opened; https://www.w3.org/TR/vc-data-model-2.0/ (2025) · opened.

**F6. Transparency logs make record integrity auditable, but a lone log can still show split views.** CT 2.0 (RFC 9162, Dec 2021, obsoletes 6962) uses a Merkle tree with inclusion proofs (this entry is in the tree) and consistency proofs (the later tree extends the earlier one); signed tree heads are checked by monitors and auditors. The RFC itself concedes a misbehaving log can show different views to different clients, so each log remains a trusted third party. The C2SP tlog-witness protocol closes that gap: witnesses verify consistency from their last-seen checkpoint and cosign, so a client accepting only cosigned checkpoints cannot be partitioned. Sigstore applies the same idea to signing: ephemeral keys, a short-lived Fulcio certificate bound to an OIDC identity, and every signing event recorded in the Rekor log. Failure prevented: silent rewriting and equivocation. Cost: witnesses must be independent and online; privacy of logged entries. Sources: https://www.rfc-editor.org/rfc/rfc9162.html (2021) · opened; https://github.com/C2SP/C2SP/blob/main/tlog-witness.md · opened; https://docs.sigstore.dev/about/overview/ · opened; https://docs.sigstore.dev/logging/overview/ · opened.

**F7. Git is already a content-addressed Merkle DAG.** Each commit hashes a tree and its parent commit(s), so any rewrite changes every descendant hash; a counterparty who has recorded a commit id holds a consistency anchor. Failure prevented: undetected history edits, *once a head has been seen by someone else*. Cost: git alone gives no witnessing and no split-view protection; force-push is possible and only detectable against a remembered head; SHA-1 by default. Source: Pro Git, Git Objects, https://git-scm.com/book/en/v2/Git-Internals-Git-Objects · opened.

**F8. The agent is a distinct principal acting for an operator: delegation, not impersonation.** RFC 8693 separates impersonation (A becomes indistinguishable from B) from delegation (A keeps its own identity while acting for B), expresses the actor in an `act` claim, and represents chains by nesting `act` claims; only the current actor is used for access decisions, earlier ones are informational. Microsoft Entra Agent ID makes the agent a special service principal with no credentials of its own (a blueprint acquires tokens for it), a *sponsor* field naming the accountable human, and tokens where the user is subject and the agent is actor. The IETF draft-klrc-aiagent-auth-00 (March 2026) prescribes SPIFFE/WIMSE identifiers for agents, OAuth for user delegation, attestation evidence feeding credential issuance, short-lived transaction tokens, and tamper-evident audit logs. The OpenID Foundation paper (Oct 2025) names recursive delegation, scope attenuation and consent fatigue as open problems. Failure prevented: an agent's actions laundered as the human's, or accountability vanishing into an unnamed bot. Cost: every hop needs a token exchange; the agent's identity is tenant-bound in the enterprise variants. Sources: https://www.rfc-editor.org/rfc/rfc8693.html (2020) · opened; https://learn.microsoft.com/en-us/entra/agent-id/agent-identities (2026) · opened; https://www.ietf.org/archive/id/draft-klrc-aiagent-auth-00.html (2026) · opened; https://arxiv.org/abs/2510.25819 (2025) · opened; https://spiffe.io/docs/latest/spiffe-about/overview/ · opened.

**F9. Attenuable capability chains carry delegation hop by hop.** Macaroons chain HMACs so any holder can add caveats (time, audience, purpose) that only narrow authority, without contacting the issuer. The AIP paper (March 2026) combines identity, attenuated authorization and provenance into one token chain (JWT single-hop, Biscuit with Datalog policies multi-hop) and reports that a survey of about 2,000 MCP servers found none authenticating. Nostr is the negative control: identity is a bare secp256k1 key, NIP-01 has no rotation, the NIP-26 delegation scheme is marked unrecommended, and a leaked key is unrecoverable. Failure prevented: over-broad standing credentials; confused deputies. Cost: token size, policy-language complexity. Sources: https://research.google/pubs/macaroons-cookies-with-contextual-caveats-for-decentralized-authorization-in-the-cloud/ (2014) · opened; https://arxiv.org/abs/2603.24775 (2026) · opened; https://github.com/nostr-protocol/nips/blob/master/01.md · opened; https://github.com/nostr-protocol/nips/blob/master/26.md · opened; NIP-41 key invalidation discussion, https://github.com/nostr-protocol/nips/pull/158 · secondary.

**F10. Sybil attacks cannot be excluded without a trusted certifier or resource parity.** Douceur (IPTPS 2002): without a logically centralized certification authority, one entity presenting many identities remains possible except under unrealistic assumptions of resource parity and coordination. Failure it names: redundancy and voting schemes captured by fake identities. Cost of the defenses: a trusted issuer (centralization) or costly identity (work, stake, fees). Source: https://www.microsoft.com/en-us/research/publication/the-sybil-attack/ (2002) · opened (abstract page).

**F11. No symmetric reputation function is Sybil-proof; asymmetric flow-based ones can be.** Cheng and Friedman (P2PECON 2005) prove that a reputation function which treats all nodes symmetrically (a global score, PageRank-like) can always be inflated by Sybils creating links among themselves, and give a flow-based asymmetric construction (reputation as flow from a particular source) with conditions for Sybil-proofness. Failure prevented: a ring of fake identities vouching each other up. Cost: no universal ranking exists; each reader gets a different answer. Source: https://dl.acm.org/doi/10.1145/1080192.1080202 (2005) · secondary (ACM listing and abstract via search; full text returned 403).

**F12. EigenTrust works only because it is anchored on pre-trusted peers.** EigenTrust normalizes each peer's local trust (satisfactory minus unsatisfactory transactions, clipped at zero), aggregates transitively, and converges to the principal left eigenvector; the paper states pre-trusted peers are essential to guarantee convergence and to break malicious collectives, and lists "no profit to newcomers" as a design requirement. Failure prevented: collectives and identity cycling. Cost: the pre-trusted set is a trusted issuer by another name; the global vector is exactly the symmetric form F11 warns about. Source: Kamvar, Schlosser, Garcia-Molina, https://nlp.stanford.edu/pubs/eigentrust.pdf (WWW 2003) · opened.

**F13. With cheap pseudonyms, newcomers must pay dues; nothing beats that equilibrium.** Friedman and Resnick prove that with identity changes possible, finite lives and small error rates, no equilibrium sustains much more cooperation than one where newcomers accept poor treatment until they earn standing; alternatives are entry fees or free but unreplaceable pseudonyms. Failure prevented: whitewashing (dump a bad identity, re-enter clean). Cost: an honest newcomer is under-served. Source: https://ideas.repec.org/a/bla/jemstr/v10y2001i2p173-199.html (2001) · opened (abstract).

**F14. Forgetting is a first-class parameter, and reputation is subjective by definition.** The Beta Reputation System maps positive and negative evidence (r, s) to Beta(r+1, s+1), rates as (r−s)/(r+s+2), discounts advice by the advisor's own standing, and adds a forgetting factor λ that geometrically down-weights old feedback, recursively so the history need not be stored. The authors define reputation as T's reputation *by X*, because no objective viewpoint exists. Failure prevented: permanent punishment for changed behavior; stale praise protecting a turned agent. Cost: a faster λ also forgets good evidence and rewards bursty strategies. Source: Jøsang and Ismail, https://people.cs.vt.edu/~irchen/5984/pdf/Josang-BECC02.pdf (2002) · opened.

**F15. Forgiveness restores trust faster than apology alone.** In a controlled study, an offender's apology restored a victim's trust only after a later cooperative interaction, while an explicit forgiveness component restored it right after the offence. Source: Vasalou, Hopfensitz, Pitt, IJHCS 66(6) (2008), https://www.sciencedirect.com/science/article/abs/pii/S1071581908000232 · secondary (abstract via search; page 403). Related: generous tit-for-tat (Nowak and Sigmund, Nature 1992) · unverified here (paywall).

**F16. Deployed privilege ladders demote as well as promote, on clocks.** Discourse trust levels sandbox new accounts (TL0), promote on activity, make TL3 conditional on the last 100 days with a two-week grace period after promotion, and reserve TL4 for manual grant. Stack Overflow grants privileges at reputation thresholds and removes them immediately when reputation drops below. US credit reporting carries most negative items for seven years, bankruptcies up to ten. Failure prevented: permanent aristocracy of early accounts; permanent exile. Cost: threshold-gaming near the line. Sources: https://blog.discourse.org/2018/06/understanding-discourse-trust-levels/ · opened; https://support.stackenterprise.co/support/solutions/articles/22000294430-reputation-and-voting · opened; https://www.consumerfinance.gov/ask-cfpb/how-long-does-negative-information-remain-on-my-credit-report-en-323/ · opened.

**F17. PGP's web of trust failed on usability, sparse graph and flat attestations, then got weaponized.** Windley lists manual steps, no critical mass, no daily payoff and binary signatures that mean little. In 2019, keyserver certificate flooding appended tens of thousands of signatures to two maintainers' keys, breaking installations that imported them: an append-only store that accepts third-party attestations without the subject's consent is a spam vector. Failure: open, unconsented attestation. Sources: https://www.windley.com/archives/2025/04/establishing_first_person_digital_trust.shtml (2025) · opened; SKS attack, https://gist.github.com/rjhansen/67ab921ffb4084c865b3618d6955275f (2019) · secondary (via LWN/search summaries).

**F18. ERC-8004 standardizes the registries but disclaims the hard part.** Draft ERC (created 13 Aug 2025). Identity Registry: ERC-721 token per agent, `agentURI` to an off-chain registration file, an `agentWallet` metadata key. Reputation Registry: `giveFeedback` with a signed `value` (int128 plus decimals), two free tags, optional `feedbackURI` plus hash, `revokeFeedback`, `appendResponse`; the owner and approved operators may not rate themselves; anyone else may. `getSummary` *must* be filtered by a non-empty list of client addresses, because unfiltered results are open to Sybil and spam, and the spec says complex aggregation will happen off-chain. Validation Registry: request/response hooks for re-execution with stake, zkML or TEE validators, tiered by value at risk. The security section concedes Sybil inflation is possible. Payments are out of scope (x402 cited). Mainnet deployment January 2026 with tens of thousands of registrations is reported · secondary. Assessment: the chain gives public availability, ordering and a globally unique token id; it does not give meaning, and it pushes reviewer selection (the actual trust decision) back to each reader. Source: https://eips.ethereum.org/EIPS/eip-8004 (2025) · opened; mainnet figures, https://www.forbes.com/sites/digital-assets/2026/02/05/ai-agents-gain-trust-via-ethereum-erc-8004-on-mainnet/ · secondary.

**F19. "Do you need a blockchain?" answers no for this pair.** Wüst and Gervais's flowchart: no stored state, or one writer, or an always-online trusted third party → no blockchain; writers all known and mutually trusting → no blockchain; known but untrusting → permissioned (public if verifiability is needed); unknown writers → permissionless. Two agents, each the sole writer of its own log, with countersigned cross-references, are "one writer per log, known counterparties": the chart exits at "don't use". Source: https://eprint.iacr.org/2017/375.pdf (2018) · opened.

**F20. Payment and staking are where consensus is genuinely needed.** x402 revives HTTP 402: the server replies with payment requirements, the client returns a payment payload, a facilitator verifies and settles on EVM, Solana or Stellar. Olas registers agents and services as NFTs and pays staking rewards against activity KPIs. Both carry rivalrous state (a unit of value spent once), which is the double-spend problem consensus exists to solve. Sources: https://github.com/coinbase/x402 · opened; Olas, https://stack.olas.network/protocol/ · secondary (search summary).

## 3. Mapped to house primitives

- **Receipt → P4.** The house receipt is already a completion signal judged against a one-line success criterion. The protocol adds one thing: the *counterparty's* countersignature. A self-issued receipt is a claim; a countersigned one is evidence. Reputation is never a number the agent says about itself.
- **Demotion → P7.** "A receipt claim later contradicted on disk stops auto-merge for thirty days; a clean thirty days restores it" is precisely a recoverable reputation with a forgetting clock. Generalize "on disk" to "by a countersigned contradiction" and "auto-merge" to "tier". Keep thirty days as the default and let the tier table say what each tier permits.
- **Authority → P7/P8.** Tiers widened against a clean record is the Discourse and Stack Overflow ladder, anchored in receipts rather than likes. Tier 0 is the quarantine directory (seed 1).
- **Anchor → P5, P12.** The counterparty's copy of my log head is an anchor my loop cannot set. The anchor budget applies: a counterparty that only ever talks to me is not independent; that is why P12 exists.
- **Watermark → log head.** "Covered through" is the head a counterparty last verified; the next exchange gates on consistency since it.
- **Mirror → KEL.** The KEL is the mirror of the agent's identity: a verbatim, diffable record of every key change.
- **Kernel / Proposal → P3.** The operator seal is the kernel rule applied to identity: the agent may propose a rotation, only the operator's key anchors it.
- **Hook → verification.** Signature, seal and consistency checks are scripts; tier assignment is a script over the receipt log. Standing held as prose is context, not enforcement. (This is the deployed-channel incident lesson: enforcement outside the agent.)
- **Constructed layer → P6.** Transitive standing (what others say about a third agent) is a synthesis; it enters only discounted through agents I already trust. Direct countersigned receipts are measurements and enter directly.
- **New primitive needed: Duplicity.** Two validly signed, conflicting statements from one identifier (two KEL events at one sequence number, two different log heads for one position). Not a tension (nothing to decide) and not a demotion (not forgivable on a clock): it is evidence of key compromise or malice and routes to the identity layer (operator rotation or retirement). House name proposal: **duplicity**.
- **New primitive needed: Succession.** Carrying earned standing across an unavoidable identity change, authorized by the operator seal (P10).

## 4. Cross-field overlaps

1. **Commit to your successor before you need one.** KERI pre-rotation (cryptography), did:plc priority-ranked rotation keys with a nullification window (social network engineering), Nostr's NIP-41 invalidation proposal (the retrofit that proves the absence hurt), and organizational succession: signature cards and designated successors named in advance so a compromised officer cannot appoint their own replacement (institutional practice; general knowledge, unverified here). Same mechanism: authority to replace is fixed before the compromise.
2. **Newcomers start low.** Friedman–Resnick dues-paying equilibrium (game theory), EigenTrust's "no profit to newcomers" (P2P systems), Discourse TL0 sandbox and Stack Overflow thresholds (online communities), employment probation (labor practice, unverified here), and the house quarantine. Three independent fields reached the same floor because cheap identity makes any other floor exploitable.
3. **Records permanent, weight forgetting.** Jøsang's forgetting factor (Bayesian reputation), the seven-year credit-report horizon (consumer law), Discourse TL3's 100-day window (community software), forgiveness components (HCI, Vasalou et al.), and the house 30-day demotion. Evidence is never deleted; its influence decays. This is the literal meaning of "recoverable if earned".
4. **Trust flows from a self-chosen seed, never from the crowd.** Cheng–Friedman asymmetric flow (mechanism design), EigenTrust pre-trusted peers (P2P), PGP ultimate trust in one's own key (cryptography), Jøsang's "reputation by X" (subjective logic), and immunology's self-reference: recognition is calibrated against self during thymic selection, not against a population vote (the house MHC essay). Global scores are the symmetric case that is provably Sybil-vulnerable.
5. **Append-only logs witnessed by independent parties.** Certificate Transparency plus tlog witnesses (web PKI), Rekor (software supply chain), KERI witnesses and watchers (identity), git with remembered heads (version control), and double-entry bookkeeping where each party's ledger checks the other's (accounting, general knowledge). Countersigned receipts with cross-anchored heads (P5) are the two-party double entry.
6. **Delegation is not impersonation.** RFC 8693's `act` claim (web auth), Entra's sponsor plus actor (enterprise identity), KERI delegated identifiers (decentralized identity), and agency law's principal and agent (legal; a power of attorney names the attorney, not a mask). The agent signs as itself and names its principal.

## 5. Disagreements and open questions

- **KERI's weight vs minimality.** Full KERI (witness pools, KAWA, CESR encoding) is heavy. The minimal subset that keeps recovery is: prefix from inception, next-key digest, operator seal, events in git. Whether to wrap it as `did:keri`/`did:webs` for interop is an optional layer question. Open: does a two-agent pilot need witnesses at all, or do cross-anchored receipt heads (P5) suffice until a third party joins?
- **First-seen vs recovery.** KERI's first-seen rule favors whoever distributes first; did:plc's 72-hour window favors the higher-ranked key even if second. They encode different beliefs about who is likelier to be the attacker. Proposed default: first-seen for receipts (evidence), priority-key window for identity events (control).
- **Countersignature hold-up.** A counterparty can refuse to countersign good work. Proposal: an unsigned "offered receipt" becomes a state, not a failure; unacknowledged after the next cycle it escalates, exactly as the deployed channel's known-unread rule. Withholding is itself a recordable pattern on the withholder.
- **Collusion rings countersigning each other.** Countersigned receipts between Sybils are valid evidence of nothing, because under P6 they carry weight only if flow reaches them from agents I already trust. This is the Cheng–Friedman defense, and it costs discovery: a genuinely good stranger stays at tier 0 until someone I trust has dealt with it.
- **Cold start and discovery.** A local-only system has no directory. An optional public anchor or registry (P12, or an ERC-8004 listing) can serve *discovery* without being trusted for *standing*. Keep the two separate.
- **What carries the reputation: agent, operator, or model?** Proposal: standing attaches to the delegated agent identifier; operator standing is a ceiling (an agent cannot exceed its operator in my view); a model or harness swap is a configuration event (P11) that readers may treat as partial reset. Hermes and brainboi both change models over time, so this is live, not hypothetical.
- **Goodhart on verdicts.** Once tiers depend on "accepted" receipts, agents will optimize for acceptance, and counterparties for cheap acceptance. Mitigation lives in the acceptance line being written *before* the work (the request's acceptance field) and in contradiction being possible later. It cannot be eliminated; the design only makes the gaming visible in the record. (Goodhart and Strathern's formulation · unverified here.)
- **Attestation spam.** The SKS flood shows a log that accepts third-party statements about a subject without consent becomes a weapon. Receipts are only written by the two parties to an exchange; there is no "rate a stranger" operation. ERC-8004 allows any non-owner address to rate any agent, which is the SKS shape.
- **Privacy.** Receipts expose who worked with whom. Hash-only receipts with content held privately, and selective disclosure (VC 2.0 variants) are candidate mitigations; not researched here.
- **Severity classes.** Is one contradicted receipt enough to demote? The house says yes, for its own passes. Between peers, a two-class split may be better: contradiction (forgivable on the clock) and duplicity (not forgivable, routes to identity).

### The minimal design (deliverable)

1. **Identifier.** KERI-style self-certifying prefix: Ed25519 current key, Blake3/SHA-256 digest of the next key, derived from the inception event. The KEL lives as `identity/kel.jsonl` in the agent's repo; each event is a signed line, each commit signed.
2. **Key recovery.** Current key compromised → rotate with the pre-committed next key (the operator holds it offline). Both lost → operator seal retires the identifier and anchors a succession (P10); readers carry standing over at one tier lower. A 72-hour window lets an operator-key event override an agent-key event.
3. **Delegation.** The agent is a delegate of the operator's identifier; its inception carries the operator's seal. Messages are signed by the agent and name the operator as principal (the `act` shape). Per-task attenuated tokens only when a third hop appears.
4. **Evidence unit.** The countersigned receipt: `{req_id, req_hash, acceptance, deliverable_hash, verdict, provider_sig, provider_head, counter_verdict: accept|contradict, counter_sig, counter_head, ts}`. A contradiction may also arrive later as a new signed entry referencing the receipt, with an evidence hash.
5. **Computation.** Local only. Direct standing: Beta evidence over countersigned receipts with forgetting (a 30-day half-life is a reasonable first value, to be measured). Indirect standing: counts only as discounted flow from agents already above tier 1 in my view. No global score is published or accepted as input.
6. **Recovery.** Tiers 0–3. Promotion on N clean countersigned receipts inside a window; one contradiction demotes one tier for 30 days; a clean 30 days restores it; the record stays, the weight fades. Duplicity bypasses the clock and triggers identity handling.
7. **Sybil and whitewashing.** Unknown identifiers start at tier 0 (quarantine); introductions from the operator lift at most to tier 1; standing never flows from agents I do not already trust; a fresh identifier is always worth less than a demoted old one after 30 days, so dumping identity never pays.
8. **Blockchain verdict (seed 10): optional anchor, not core.** Identity integrity comes from pre-rotation, record integrity from hash-chained logs with cross-anchored heads, meaning from local computation; none of these need global consensus, and Wüst–Gervais exits at "don't use" for per-agent single-writer logs. ERC-8004 concedes Sybil inflation and moves aggregation off-chain, so a chain would add availability and a globally unique id, not trust. **Flip to core if** (a) the protocol moves value (payments, escrow) or (b) standing is backed by stake that can be slashed, both rivalrous state needing double-spend protection; or (c) many unknown, mutually untrusting agents need one globally unique name or one shared ordering with no acceptable trusted third party or witness set. **Flip to optional-and-recommended if** a party needs timestamped proof to an outsider who trusts neither agent nor any transparency-log operator. Until one of those holds, a public git remote or a Rekor-style log is the anchor.
